# ADR-005：模块化工程结构约定（UI / 数据模型 / 逻辑分离）

- 状态：**已接受**
- 日期：2026-08-29
- 提出人：用户（"项目结构需要做到模块化开发：UI、数据模型、逻辑代码要分成不同的文件；重复使用的功能要封装"）

## 背景

M2 起代码量将倍增（引擎/路由/管理/记忆/UI）。必须在写之前定结构，避免事后重构；同时这是面试"工程素养"的直接证据。

## 决策

### 目标目录树

```
src/t2s/
├── models/     # 跨层共享数据模型（纯 pydantic：TaskRequest/Answer/Budget/Session/QAPair…）
├── llm/        # 基础设施：LLM 客户端（已存在）
├── tools/      # 工具实现（已存在；模块私有模型留模块内，如 ChatMessage 留 llm/types.py）
├── storage/    # 存储访问层（M3/M4）：SQLite/Chroma 代码只允许出现在这里
├── manager/    # 管理层逻辑（M3）：上下文装配 / schema 召回 / 记忆读写 / 预算
├── executor/   # 执行层逻辑（M2）：engine.py / guard.py / prompts.py（提示词模板独立成文件）
├── router/     # 路由层逻辑（M3）：intents.py / permissions.py
├── ui/         # 展示层（M3/M6）：repl.py / web/ —— 只做输入输出与渲染，零业务逻辑
└── utils/      # 跨模块复用纯函数（截断 / 时间 / 文本处理），不 import 项目内其他模块
```

### 依赖方向（单向，禁止回环）

```
ui → router → manager → executor → {tools, llm}
models：被所有层 import，自身不 import 项目内其他层
```

> 修正（CHG-004）：**storage 可被 manager 与 executor 访问**——管理层的会话/记忆职责必须读写存储，执行层工具要查业务库；原表述把 storage 仅挂在 executor 之下是不完整的。

### 封装规则

1. **UI / 数据模型 / 逻辑三分**：UI 只消费结构化结果做渲染；models 只有字段与校验、无业务逻辑；业务逻辑不得直接 touch SQLite/Chroma（必须过 storage）。
2. **复用即抽取**：同一逻辑出现第 2 处必须抽取到 utils 或归属模块的公共接口（单人项目不留"三处再抽"的宽容度）。
3. **安全单点**：SQL 护栏等安全逻辑只允许单点实现（tools/sql_tools.py），UI 与引擎不得复制旁路。
4. **提示词即资产**：所有 LLM 提示词模板独立成 `executor/prompts.py`（或模板文件），禁止内联字符串散落逻辑中。

### 现状迁移说明

M0/M1 产物已符合约定（llm / tools 分层清晰，配置独立），**无需回溯重构**；自 M2 起强制执行本约定，PR 评审（自审）按依赖方向检查。

## 备选与否决理由

- **单文件大杂烩**：不可测、不可讲、违反用户明确要求。
- **按技术分层（models/views/controllers 式）**：对 agent 项目噪声大——本项目的天然边界是"三层架构 + 基础设施"，业务内聚优先于技术分层。

## 影响面

- AGENTS.md §1 更新指向本 ADR；M2 起所有新代码按此树落位；违反即为评审问题。
