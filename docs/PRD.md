# Test2SQL PRD（产品需求文档）

- 版本：1.0（2026-08-29）
- 来源：grill-me 九轮拷打共识（ADR-001）+ 两份调研报告 + `docs/design.md`
- 文档层级：本文档回答"做什么、给谁做、做到什么程度算好"；技术方案见 design.md；两者冲突时以最新 ADR/CHG 为准（ADR-004）
- 读者：未来的自己、面试官、以及任何接手的代理（配合 `docs/handoffs/` 使用）

---

## 1. 背景与问题

用户在金融科技公司实习期间观察到：公司服务的对象（证券公司、银行）中，大量业务人员不熟悉 SQL，取数依赖"向数据组提工单 → 排队 → 人工写 SQL → 回发 Excel"的流程。企业里约 80% 的取数需求是重复劳动，且业务人员真正的困难不是"没有数据"，而是**不知道表在哪、口径是什么、SQL 怎么写**。

行业背景（DB-GPT 调研报告 §4）：企业对 agent 的诉求是**可控优先**——权限、审计、确定性，远高于"自主智能"。因此本产品是**工作流增强型 agent**：固定护栏内的受控自主，而非自由 ReAct 玩具。

## 2. 产品定位

**一句话**：面向证券/银行业务人员的自然语言取数助手——用中文提问，返回 SQL、表格与图表，替代"提数工单"流程。

- **替代物**：业务部门 → 数据组的取数工单（邮件/IM 往返，小时~天级延迟）
- **交付形态**：CLI（开发工具）+ FastAPI Web 单页（业务人员入口）+ 交互式架构图（自用）
- **数据边界**：demo 库与真实券商业务同构，数据全部合成（合规红线，见 NFR-1）

## 3. 目标与非目标

### 目标（Goals）
1. 业务人员零 SQL 基础完成"单表查数、多表 JOIN、聚合统计"三类高频取数（golden 集前四档）
2. 全链路可审计：谁、何时、问了什么、执行了什么 SQL、返回多少行
3. 记忆系统带来可测量的准确率提升（消融实验产出 Δ%）
4. 面试叙事完整：三层架构 + ReAct 引擎 + 记忆 + 防护 + 评测，每个设计点都能落到代码与数字

### 非目标（Non-Goals，来自 ADR-001 §12 的明确裁剪）
- ❌ 任何写操作 / DDL（只读硬边界）
- ❌ 多方言适配（二期接 MySQL 验证抽象，不进 MVP）
- ❌ 复杂看板（单图即可）、Dream 式记忆固化、用户画像
- ❌ 裁判模型、Spider/BIRD 刷榜（了解榜单即可）
- ❌ 使用任何真实客户数据

## 4. 目标用户与画像

| 画像 | 描述 | 核心诉求 | 优先级 |
|---|---|---|---|
| **业务人员小王** | 券商运营岗，Excel 熟练、SQL 零基础，日均 3~5 次取数 | 用大白话问到数；口径有歧义时被追问而不是被糊弄 | P0 |
| **数据组老李** | 被工单淹没的分析师 | 工单变少；可疑查询有审计可查；agent 失败时转人工而不是硬编 | P0（受益者）/P1（审计视角） |
| **面试官** | Agent 工程岗位面试官 | 追问任何设计点都能落到文件行号与评测数字 | P0（真实受众） |

反画像：DBA / 运维工程师——不做慢查询诊断、索引建议等运维功能（grill 第 1 问否决项）。

## 6. 功能需求（FR）

| # | 需求 | 优先级 | 里程碑 | 验收要点 |
|---|---|---|---|---|
| FR-1 | 自然语言取数主流程：问题 → TaskRequest → 上下文装配 → SQL 生成 → 校验 → 执行 → 表格 | P0 | M2/M3 | golden 单表/JOIN/聚合三档可跑通 |
| FR-2 | 工具五件套：search_schema / get_schema / validate_sql / execute_sql / ask_user | P0 | M1 ✅ | 35 测试 + 冒烟九项（CHG-002） |
| FR-3 | 计划无关 ReAct 引擎：决策→工具→观察回填→循环；错误即观察 | P0 | M2 | 协议不变量（先声明后回填）有测试钉住 |
| FR-4 | 四层死循环防护：步数上限+强制总结 / 重复+振荡检测 / 错误回喂≤2 / 墙钟 | P0 | M2 | 四个故障注入场景分别被对应层拦截 |
| FR-5 | 诚实失败：步数耗尽→无工具总结；不可解→转人工/提工单接口 | P0 | M2 | 降级路径有日志、有终点文案 |
| FR-6 | 路由层：意图分类、危险请求拦截、会话绑定（同会话串行）、权限初检（只读全表白名单） | P0 | M3 | 危险请求 100% 拦截（golden 含此项） |
| FR-7 | 多轮会话：历史窗口裁剪 + token 预算；澄清限次 | P0 | M3 | US-2/US-3 通过 |
| FR-8 | 记忆三层：短期会话 / 成功 QA 样例库（双通过入库、点踩删除、few-shot top-3）/ 业务口径库 | P0（样例库）/P1（口径库） | M4 | 相似问题命中样例；检索失败降级直答 |
| FR-9 | 评测体系：golden 50（五档分层）+ 结果集比对 + 记忆消融 + 回归纪律 | P0 | M5 | 消融报告产出 Δ%；改 prompt 必跑回归 |
| FR-10 | 交付面：REPL（P0，开发工具）+ FastAPI 单页 Web（P1，业务入口） | P1 | M6 | Web 端完整走通取数 + 图表 |
| FR-11 | 快路径双轨：简单问题走强制计划模式，复杂问题升级 ReAct | P2（二期） | 二期 | 零重构（引擎已计划无关） |
| FR-12 | 审计日志：每次取数全字段落库 | P0 | M3 | US-4/US-7 通过 |

## 7. 非功能需求（NFR）

| # | 需求 | 指标 |
|---|---|---|
| NFR-1 | 安全合规 | 零真实客户数据；只读连接（mode=ro）；写操作黑名单；审计字段完整 |
| NFR-2 | 性能 | execute_sql 超 30s 中断；单 turn 墙钟 120s；简单问题端到端 P95 ≤ 60s（LLM 主导，M5 实测校准） |
| NFR-3 | 成本 | 单问题平均 LLM 调用 ≤ 6 次（M5 建基线）；快路径（二期）目标 ≤ 2 次 |
| NFR-4 | 准确率 | M5 建立 golden 基线；目标：记忆消融相对提升 ≥ 5 个百分点——**若实测不达标，如实报告并归因，评测纪律优先于指标好看** |
| NFR-5 | 可观测 | 每问完整 trace：步数、每步工具、token、耗时、终止原因 |
| NFR-6 | 可移植 | LLM 可配置切换（OpenAI 兼容：DeepSeek/Qwen/GLM）；SQLite→MySQL 抽象预留 |
| NFR-7 | 可维护 | 模块化结构（ADR-005）；测试基线只增不减；文档纪律（ADR-002） |
| NFR-8 | 可测试 | 管理层零 LLM 全单测；LLM 层 MockTransport；评测集独立 marker |

## 8. 评测与成功指标

- **golden 集**：50 条起步，五档分层（单表 15 / 多表 JOIN 15 / 聚合 10 / 时间口径 5 / 歧义追问 5），每条含标准 SQL 与期望结果；随用户采纳闭环增长
- **主指标**：执行**结果集比对**准确率（非字符串比对）；辅助：语法有效率、平均步数、平均 token、修复成功率、澄清触发率
- **记忆消融**：开/关样例库对比 → Δ% 写进面试材料
- **回归纪律**：改 prompt/工具/护栏 → `pytest`（单元）+ `pytest -m eval`（golden）双绿

## 10. 风险与缓解

| 风险 | 影响 | 缓解 |
|---|---|---|
| golden 准确率不达标 | 面试叙事空心化 | 澄清机制兜住歧义题；样例库拉动重复模式；诚实报告归因（NFR-4） |
| LLM 输出不稳定（JSON/工具参数） | 引擎崩溃 | schema 校验 + cast 矫正 + 错误即观察（已实现） |
| 死循环烧钱 | 成本/体验双输 | 四层防护（FR-4）+ 预算随 TaskRequest 下发 |
| 范围蔓延 | 单人项目烂尾 | Non-Goals 清单 + ADR/CHG 纪律：任何新增先过"是否推翻 Non-Goals" |
| 合规误用真实数据 | 红线 | 合成数据 + 合成号段 + AGENTS.md 红线 |

## 11. 未决问题（Open Questions）

1. Web 端 ask_user 澄清的交互形态：同步表单还是流式追加？（M6 前定）
2. 图表渲染选型：后端出 JSON + 前端轻图表库，还是 LLM 选型 + 白名单（DB-GPT 式）？（M6 决定）
3. per-user 权限模型（库表白名单 → 行级权限）何时启用？（一期只读全表，接口已预留）
4. golden 集的"采纳闭环"由谁确认：自动入库 + 抽样人审，还是全部人审？（M4 定）

## 12. 附录：术语

- **快路径**：强制计划模式的固定流水线（二期），与 ReAct 共享同一引擎
- **四层防护**：步数上限 / 打转检测 / 错误回喂限次 / 墙钟超时（ADR-001 D6）
- **双通过**：validate_sql 通过且 execute_sql 无错，才允许写入样例库
- **结果集比对**：agent SQL 与金标 SQL 各自执行后比对结果集，而非比对 SQL 文本
