# CHG-014：v2 回归修复——LIMIT 保序、行数诱导消除、schema 缓存与比对模糊对齐

- 日期：2026-08-31
- 动机：v2 首轮全量回归 **70%**（35/50），未守住 78% 基线（JOIN 档 67%→40%，语法有效率 96%→90%）。按 diagnose 纪律归因后修复。
- 类型：修复（三处根因 + 一处比对器增强）

## 根因归因（逐案实证，非推测）

| # | 根因 | 证据 | 修复 |
|---|---|---|---|
| 1 | **LIMIT 注入破坏 ORDER BY**：`SELECT * FROM (原语句) LIMIT n` 的子查询包裹使内层 ORDER BY 顺序保证失效（SQL 标准中子查询内排序无意义），SQLite 查询计划变化后大面积暴露——"有序不一致 N/N"全是它 | J02 完整 agent SQL 无 ORDER BY 丢失后实际返回顺序违反 DESC；v1 基线轮为侥幸通过 | 改用 sqlglot 在**原语句上**设置 LIMIT（`stmt.limit(n)`），ORDER BY 保留原位；新增保序回归锚点测试 |
| 2 | **get_schema 行数诱导**：工具返回"总行数"，模型把表行数当查询答案跳过执行（S03"产品总数 3,000"=products 行数碰巧同义、S15 明说"orders 表结构信息显示总行数为 450,000 条"） | audit content 引用表结构行数作为答案来源 | get_schema 移除总行数（要行数必须 execute_sql COUNT） |
| 3 | **get_schema 同表反复调用打转**：J06/J08/J09 stop=repeat_stop | 步数 6/9/11 的父轨迹 + 审计"确认表结构"反复出现 | get_schema per-turn 缓存：同表第二次返回缓存 + "[提示] 已提供过，请直接编写 SQL" |
| 4 | **比对器列别名/超集盲区**：A01 型（agent 列 customer_count+percentage vs 金标 risk_level+n）投影失败退严格模式误判 | 离线 diff 实证列名不匹配但语义一致 | 比对器增加**类型签名模糊对齐**（贪婪匹配数值/文本列） |

X01（12 行 vs 1 行，把"月活跃客户数"理解成列出名单）与 J10（客户常住城市混成营业部城市）为**真实口径错误**，如实保留为错。

## 验证结果

- `pytest`：**132 passed, 2 skipped**（+4：LIMIT 保序锚点、get_schema 无行数断言、per-turn 缓存、模糊对齐用例）。
- 全量回归（修复后）：**进行中**（`--tag v2-fixed`），结果将回填本文件附录。

## 经验

1. **LIMIT 注入这类"帮模型兜底"的改写必须保序**——任何对用户 SQL 的自动改写都要重验其语义（顺序/列名/别名）。
2. **工具输出会引导模型走捷径**：get_schema 附带行数 → 模型以行数作答。工具设计要审查"这个信息会被拿来干什么"。
3. 评测失败的归因必须到具体 SQL 与实际行差（离线 diff），不能停在"档位下降"的表象。
