## 1. 定位与替代叙事

**一句话**：面向证券/银行业务人员的自然语言取数助手——业务人员不熟 SQL，用中文提问，返回 SQL、表格与图表。

- **替代物**：业务部门向数据组提"取数工单"的邮件/IM 往返流程（排队 → 数据组写 SQL → 回发 Excel）。企业里 80% 的取数需求是重复劳动。
- **真实背景**：金融科技公司实习观察，客户为券商/银行，业务人员有强查数需求但无 SQL 能力。
- **合规边界（面试追问位）**：不使用任何真实客户数据——demo 库结构与真实业务同构、数据用 faker 合成；只读账号；审计日志每问必录（谁、何时、问了什么、执行了什么 SQL、返回多少行、耗时）。

## 2. 总体架构：三层职责

```
用户（REPL / Web）
   │ question
   ▼
┌─────────────── 路由层 Router ───────────────┐
│ 意图分类（取数/闲聊/危险请求）· 权限初检 ·      │
│ 会话绑定（同会话串行锁）· 组装 TaskRequest     │
└──────────────────┬──────────────────────────┘
                   ▼ TaskRequest {session_id, user_id, question,
│                    mode, budget{max_steps, timeout_s, max_repair}}
┌─────────────── 管理层 Manager（零 LLM）──────┐
│ 会话历史装配与窗口裁剪 · schema 向量召回 ·      │
│ 记忆读写（样例库/口径库）· 预算与护栏配置        │
└──────────────────┬──────────────────────────┘
                   ▼ 组装好的上下文 + 工具 schema + 预算
┌─────────────── 执行层 Executor（唯一 LLM 所在）┐
│ 计划无关 ReAct 引擎：决策→工具→观察回填→循环     │
│ 四层死循环防护 · 强制总结 · 降级接口            │
└──────────────────┬──────────────────────────┘
                   ▼ Answer {sql, table, chart?, thoughts, trace}
```

**切分原则（拷打第 3 问结论）**：管理层全部是确定性代码，可单测；LLM 只存在于执行层。呼应 DB-GPT「能用确定性代码表达的步骤，就不用模型的不确定性去换」。

**调研对应**：路由层 ≈ DB-GPT ChatScene 路由 + nanobot MessageBus/_dispatch；管理层 ≈ nanobot ContextBuilder/SessionManager + DB-GPT schema 召回；执行层 ≈ nanobot AgentRunner（去掉产品层关注点）。

**双轨预留（拷打第 2 问结论）**：执行引擎是"计划无关"的——它只知道跑步骤/调工具/回填观察。二期"快路径"= 路由层判定简单问题后，以强制计划模式（system prompt 固定步骤 + 约束工具选择）注入同一引擎，零重构。企业叙事：80% 简单查询走快路径省时省 token，20% 复杂问题升级 ReAct。

## 3. 执行层：ReAct 引擎

参照 nanobot `runner.py:465 _run_core` 的结构简化：

```python
def run(task: TaskRequest) -> Answer:
    messages = manager.build_context(task)          # 系统+历史+记忆+few-shot
    seen_args: dict[str, int] = {}                  # 重复动作检测
    for step in range(task.budget.max_steps):       # 默认 12
        ctx = governor.prepare(messages)            # 模型视图治理（绝不改持久历史）
        resp = llm.chat(ctx, tools=registry.definitions(),
                        timeout=60)                 # 单次 LLM 墙钟
        if not resp.tool_calls:
            return finalize(resp)                   # 正常终止：最终回答
        append(messages, resp.assistant_tool_calls) # 先声明后回填（协议不变量）
        for call in resp.tool_calls:                # 只读工具可并发，写类串行
            obs = registry.execute(call)            # 错误即观察，永不抛异常
            append(messages, tool_result(obs))      # 截断至 max_tool_result_chars
        guard.check(step, seen_args, messages)      # 四层防护挂点（见 §5）
    else:
        return finalize_summary(messages)           # 步数耗尽 → 一次无工具总结请求
```

**三个不变量**（来自 nanobot 报告 §3/§6，面试高频）：
1. **先声明后回填**：assistant(tool_calls) 消息必须先于 role=tool 结果入列，否则协议非法、下次请求报错。
2. **错误即观察**：工具异常一律包成错误文本 + `"[分析以上错误并尝试不同的方法]"` 回填，交给模型自纠错；只有"不可重试错误"（如写操作拒绝）标记后不再重试。
3. **模型视图 ≠ 持久历史**：上下文治理（截断/占位化）只作用在发送副本上，落盘历史追加边界不可移动。

## 4. 工具契约（五件套）

| 工具 | 签名 | 护栏 | 失败语义 |
|---|---|---|---|
| `search_schema` | `(query: str, top_k=3)` | 只读，并发安全 | 空结果提示改关键词 |
| `get_schema` | `(table: str)` | 只读，并发安全；DDL+注释+外键+3 行脱敏样例 | 表名不存在 → "Did you mean …?" |
| `validate_sql` | `(sql: str)` | 纯本地 sqlglot：语法解析+表列存在性+SELECT-only 断言 | 返回 `{valid, errors[], tables_used}` |
| `execute_sql` | `(sql: str)` | 只读账号；强制 LIMIT 100 包裹；30s 超时；写类关键字直接拒绝（**不可重试**） | DB 报错回喂观察 |
| `ask_user` | `(question: str, options?)` | 每 turn 限 2 次（防逃避任务） | 用户拒答 → 模型按假设继续并声明假设 |

**工具实现契约**（nanobot `tools/base.py` 模式）：每工具 = `name / description / parameters(JSON Schema)` + `execute()`；`to_schema()` 输出 function-calling 格式；执行前统一走 `prepare_call`：参数先 cast（"42"→42）后 validate，错误组装成给模型看的修复提示。

**为什么 validate 独立成工具**（拷打第 4 问结论）：把校验做成模型可主动调用的工具，"执行-报错"的长循环被压缩成"校验-修复"短循环（死循环防护⑥类：诱因消除）；同时它是 DB-GPT 调研报告指出其未做完的一环，属于本项目的增量点。

## 5. 死循环防护：四层 + 降级接口

| 层 | 机制 | 默认参数 | 对应故障模式 |
|---|---|---|---|
| ① 预算 | 步数上限 + 耗尽后**无工具强制总结**（把已知信息整理成答案，不抛异常） | 12 步 | 模型永不主动停 |
| ② 打转 | `(tool, args_sha1)` 连续 ≥2 次 → 注入"你在重复，换路或承认失败"；全局重复计数 ≥3 → 强停并总结 | 2 / 3 | 反复提交同一句报错 SQL |
| ③ 回喂 | 同一 SQL 的执行错误最多回喂修复 **2 次**，第 3 次把错误诚实返回用户 | 2 次 | 修复循环不收敛 |
| ④ 墙钟 | turn 120s / 单次 LLM 60s / 单工具 30s | 见左 | 网络挂死、慢查询 |

- **validate_sql 前置**属于防护第⑥类（诱因消除），随工具层一期落地。
- **降级接口**：ReAct 失败 →（二期）固定流水线重试 → **转人工/提工单**（一期留 Endpoint 与日志，企业叙事的"诚实失败"终点）。
- **二期进阶（面试讲路线）**：独立裁判小模型监视主循环轨迹判断打转（防护④类）；振荡检测升级为上下文状态哈希 A→B→A→B 识别。

## 6. 记忆系统：三层

| 层 | 载体 | 写入时机 | 检索时机 |
|---|---|---|---|
| 短期会话 | SQLite `sessions/messages` 表 | 每轮增量落盘；丢弃无声明孤儿 tool 结果 | 每轮组装上下文：窗口 N 轮 + token 预算裁剪（跨轮追问"再按月分组"） |
| 样例库（长期） | `qa_pairs` 表 + Chroma 向量 | validate+execute **双通过自动入库**；用户点踩可删 | 组装提示时按问题相似度检索 top-3 注入 few-shot |
| 口径库（长期） | `metrics_docs` 表 + Chroma | 人工维护/批量导入（"月活跃=月内有交易"类业务口径） | 问题含指标词时召回注入 |

统一 `MemoryStore` 接口；检索失败降级为无 few-shot 直接生成（不阻塞主流程，DB-GPT 降级意识）。

**明确不做**（拷打第 5 问结论）：Dream 式定时固化、经验流水位线、用户画像——为通用助手设计，Text2SQL 场景属过度设计；"知道什么不该做"本身是面试加分项。

## 7. 路由层

- **意图分类**：一次轻量 LLM 分类（取数 / 闲聊 / 危险请求），危险词（写操作、脱敏字段探询）正则前置拦截。
- **权限初检**：user → 库表白名单（一期简化：统一只读账号 + 全表白名单，接口留好 per-user 扩展位）。
- **会话绑定**：同 session 串行锁；`TaskRequest` 携带 `budget`（护栏配置由管理层注入，执行层只读）。
- 二期：难度判定 → 快路径 or ReAct 双轨调度。

## 8. 技术栈与工程约束

| 项 | 选择 | 理由 |
|---|---|---|
| Python | 3.11+（uv 新环境，不动系统 3.9） | 生态与 nanobot 对照阅读一致 |
| LLM 客户端 | **自写** httpx + pydantic，OpenAI 兼容协议 | 重试 1/2/4s 退避、超时、SSE 流式；模型配置化（DeepSeek/Qwen/GLM 任一，.env） |
| SQL 校验 | sqlglot | 语法解析、方言、表列提取一体 |
| 向量 | Chroma | pip 即用；量级小够用 |
| 存储 | SQLite（业务 demo 库 + 记忆存储） | 零部署 |
| 测试 | pytest | 管理层/工具层单测 + golden 回归 |
| UI | 裸 REPL（~100 行）+ FastAPI 单页（M6） | REPL 验证交互行为；Web 贴业务叙事 |
| **明确不引** | langchain / langgraph / fork nanobot | 循环/工具/记忆亲手实现才是本项目核心产出（拷打第 7 问结论） |

## 9. 数据与评测

- **demo 库**：12~15 张证券业务表（客户/账户/持仓/交易/行情/产品/风控），faker 合成**百万行**交易流水——大数据量激活 LIMIT/超时/索引等工程话题（拷打第 8 问结论：Text2SQL 难点在 schema 复杂度与口径歧义，不在行数；行数是执行层护栏的舞台）。
- **golden 集**：50 条起步，按"类型×难度"五档分层（单表 15 / 多表 JOIN 15 / 聚合 10 / 时间口径 5 / 歧义追问 5），每条含标准 SQL 与期望结果；随用户采纳**闭环增长**（采纳查询进候选池，人工确认入集）。
- **指标**：执行**结果集比对**准确率（比字符串比对公平）、语法有效率、平均步数、平均 token 成本、修复成功率。
- **消融实验**：关/开样例库对比准确率 → 产出"记忆系统带来 Δ%"的面试硬数字。
- **回归纪律**：改 prompt/工具必跑 `pytest -m eval`。

## 11. 面试快答（追问预测）

- **为什么三层？管理层为什么零 LLM？** → 职责单一可单测；确定性代码替代模型不确定性（DB-GPT 哲学）；LLM 收敛到执行层一处。
- **为什么 ReAct 而不是纯流水线？** → 学习目标 + BIRD 头部方案同构（难题上多步探索赢单发）；引擎计划无关，流水线是其特例，双轨演进零重构。
- **死循环怎么办？** → 四层组合拳逐层讲故障模式；知道六类全景（预算/打转识别/结构预防/元认知/回退/诱因消除），裁判模型是进阶路线。
- **记忆为什么是样例库而不是对话摘要？** → Text2SQL 的知识形态是 (question, SQL) 对；few-shot 检索是 Vanna 验证过的最大准确率杠杆；对话膨胀用窗口裁剪就够。
- **工具报错怎么处理？** → 错误即观察 + 修复提示回喂；限次；不可重试错误分类；诚实失败优于幻觉。
- **权限/审计怎么落地？** → 只读账号 + 表白名单 + 全链路审计日志；写操作关键字硬拒绝。
- **怎么证明有效？** → 分层 golden 集 + 结果集比对 + 记忆消融 Δ%；改必跑回归。

## 12. 明确不做（范围裁剪）

Dream 式记忆固化与用户画像 ｜ 裁判模型（二期讲）｜ 写操作/DDL ｜ 多方言适配（二期接 MySQL 验证抽象）｜ 复杂看板（单图即可）｜ Spider/BIRD 上榜刷分（了解榜单与主流水平即可）｜ 真实客户数据（合成数据替代）。
